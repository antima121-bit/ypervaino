BOT REPOSITORY — HIGH-LEVEL UNDERSTANDING (KT)
================================================
Repo path: ~/src/bot
Main app: kb_bot/ (Python 3.11, FastAPI, Uvicorn)
Entry point: kb_bot/kb_bot/bot.py

Purpose
-------
Multi-channel conversational AI backend for thelevel.ai's Virtual Assistant (VA)
product. Powers knowledge + skills + workflow bots over chat and voice. Handles
LLM orchestration (LangGraph), RAG, telephony (Twilio/Retell/Vapi/SignalWire),
CRM connectors, guardrails, analytics, and internal service APIs.

HOW THE BOT READS CONFIG AT RUNTIME
-----------------------------------

1. Assistant identity
   - WebSocket/HTTP passes tenant + origin_id (or assistant_id).
   - get_published_or_draft_assistant() loads Assistant + settings from Mongo.
   - Channel (chat vs voice) drives prompts, tools, and LLM resolution.

2. Skills & tools
   - LLMAgent documents = skills (trigger, general_prompt, tools, knowledge_base).
   - Tool documents hang off agent_id; ToolsAPI.enrich_tools() loads API configs.
   - Flow-bound agents have flow_id set; standalone skills have flow_id=null.

3. Dialog / workflow graphs
   - Flow collection: nodes (CONVERSATION_NODE, API, Code, …), edges, triggers.
   - SESSION_START flow can override legacy orchestration to DIALOG_FLOW at runtime.

4. LLM routing (llm_config/)
   - ConfigResolver merges Mongo LLMConfiguration with hardcoded defaults.
   - Keyed by: assistant_id + channel + LLMPurpose (router, main_stream, kb_stream,
     contextual_query, standalone_query, closing_msg, …).
   - LLMFactory → LLMChainBuilder → provider (OpenAI, Vertex, Groq, custom_langchain, …).
   - Per-assistant overrides via Mongo or script:
     kb_bot/kb_bot/scripts/upsert_custom_llm_config.py
     (maps transactional_bot → main_stream, kb_bot → kb_stream).

5. Knowledge / RAG
   - Assistant.knowledge_base.resource_ids + per-skill KB.
   - RetrievalConfig per assistant_origin_id; Qdrant collection per tenant/env.
   - Atlas path optional (enable_atlas in orchestration_config).

6. Prompts
   - PromptFactory / Langfuse matrix prompts (PromptNames enum).
   - Orchestrator-specific PromptManager subclasses assemble system prompts.


ORCHESTRATION ARCHITECTURES (the “kinds of bots”)
-------------------------------------------------

OrchestrationType enum (assistants/models/orchestration_settings.py):

NEW archetypes (for newly created assistants):
  SINGLE_AGENT    → LanggraphSingleAgent — one agent, minimal routing
  MULTI_AGENT     → LanggraphMultiAgent — multiple agents with routing
  WORKFLOW_AGENT  → LanggraphWorkflowAgent — workflow-centric graph

LEGACY (still in prod for existing bots):
  DELEGATOR_V2_VOICE → LanggraphDelegator_V2_Voice_KB (DEFAULT for most live bots)
  SIMPLE             → LanggraphSimple — single react node, no router
  DIALOG_FLOW        → LanggraphDialogFlow — scripted flow graph drives turns

OrchestratorFactory (assistants/langgraph/base.py) picks the class.

--- 1) DELEGATOR_V2_VOICE (production default) ---
Graph shape (simplified):
  START → route_to_workflow (proxy)
    → single skill? go direct
    → return to last active node? resume
    → else LLM router + contextual_query → pick skill or information_agent
  INFORMATION_AGENT → KB-grounded answers (retriever tool)
  Each SKILL → sub_agent_react_node (tools + optional general_query_handler)
  HUMAN_HANDOVER (optional) → FINISH
  FINISH → exit_node (standalone query rewrite + closing-msg detection)

Best for: multi-skill bots with KB + transactional skills + router.

--- 2) DIALOG_FLOW ---
Session-start Flow graph defines nodes (conversation nodes bound to LLMAgents),
edges, and transitions ([[node: id]] references in prompts).
LanggraphDialogFlow orchestrator walks the flow instead of free-form routing.
Runtime may set effective_orchestration_type = DIALOG_FLOW when a session-start
flow exists (except SINGLE_AGENT / MULTI_AGENT / WORKFLOW_AGENT).

Best for: scripted call/chat flows (auth → billing → payment, etc.).

--- 3) SIMPLE ---
Single LangGraph react agent — no router, no information_agent split.
One node with tools + optional KB retriever.

Best for: small FAQ or single-skill bots.

(New types SINGLE_AGENT / MULTI_AGENT / WORKFLOW_AGENT are self-contained
orchestrators added in Milestone 2; legacy paths remain for backward compatibility.)


REQUEST / TURN LIFECYCLE (chat or voice)
----------------------------------------

1. Client opens WebSocket (or voice webhook establishes session).
2. SessionContext set (tenant, session_id, assistant_id, channel).
3. AssistantFactory creates LanggraphAssistant:
   - Loads Mongo models (assistant, agents, tools, flows, LLM configs).
   - OrchestratorFactory builds orchestrator + compiles LangGraph with checkpointer.
4. User message arrives → USER_QUERY event logged.
5. Per turn (run_node in base.py):
   a. Voice only: handle_voice_interruption() if user barged in mid-response.
   b. RevertController.capture() — snapshot checkpoint before new work.
   c. orchestrator graph astream() runs until stop condition.
   d. Tokens/events streamed to client via IOHandler / WebSocketContext.
   e. Events written to EventBatchLogger → writer_service → Mongo.
6. Session end → checkpoint handlers (metrics, flows, webhooks) via writer_service.


STREAMING
---------

Chat WebSocket:
  - LangGraph astream() with multiple stream modes (messages, custom, updates).
  - Skill react subgraphs: AIMessageChunk on "messages" stream → client.
  - Information agent (delegator): uses stream_prompt_llm_runnable() + StreamWriter
    (custom stream path); base.py skips duplicate "messages" chunks for that node.
  - Tool calls: streamed as structured events; mock tools in eval mode.

Voice:
  - Similar graph streaming; TTS path (Retell/LiveKit) consumes token chunks.
  - preamble_streamed sentinel after KB stream so TTS can flush before FINISH.
  - Filler audio optional (enable_filler in orchestration_config).

LLM streaming providers:
  - LangChain providers (OpenAI, Vertex, custom_langchain) support streaming.
  - SDK-only providers (openai_sdk, vertexai_sdk) are non-streaming fallbacks.


INTERRUPTIONS (primarily voice)
-------------------------------

Config: orchestration_config.enable_interrupted_response (default true).

Mechanism:
  - Client sends interruption snapshot (agent_state, backend_state, partial response).
  - handle_voice_interruption() in interruption_flow/handler.py:
    • May revert LangGraph checkpoint via RevertController (RevertibleCheckpointer).
    • Cleans orphaned tool messages from aborted turn.
    • Merges user query with partial assistant speech when appropriate.
  - PromptManager injects interruption block into KB/skill prompts when
    is_interrupted_message=true (INTERRUPTED_PROMPT_PROCESSED event in logs).

Chat: lighter interruption support via prompt blocks; voice is the primary path.

RevertController: captures pre-turn checkpoint; revert on barge-in so the bot
does not commit half-finished tool loops to history.


LLM RESILIENCE (two independent layers)
---------------------------------------

1. In-band fallback (llm_fallback.md)
   - Per request: primary model → fallback_chain with .with_retry() + .with_fallbacks().
   - Configured in LLMConfiguration or defaults.py per LLMPurpose.

2. Out-of-band failover (llm_failover.md + gcp_functions/llm_probe/)
   - Scheduled probes hit deployments; unhealthy endpoints skipped via Redis BreakerFilter.
   - deployments.yaml maps model_id → env vars for base_url/api_key (custom models).

Custom / in-house / Fireworks models:
  - Provider: custom_langchain (ChatOpenAI + openai_api_base).
  - Registry keys: main_model, router_model, cq_model, input-guardrail-model, …
  - Session affinity header (x-session-affinity) for sticky vLLM routing.

  upsert_custom_llm_config.py apply <model_id> --purpose transactional_bot \
    --assistant-id <uuid> --base-url https://api.fireworks.ai/inference/v1


WORKFLOWS vs SKILLS vs FLOWS (terminology)
-------------------------------------------

Skill (LLMAgent): LLM agent with prompt + tools; shown in UI "Skills" section.
Workflow (Workflow doc): API-builder workflow (multi-node: API, Code, Return);
  exposed as a Tool with action_type=FLOWS.
Flow (Flow doc): Dialog flow graph (conversation nodes, session triggers);
  drives DIALOG_FLOW / WORKFLOW_AGENT orchestration.
Knowledge: resource_ids on assistant or skill → Qdrant/Atlas retrieval.

COMMON DEBUGGING PATTERNS (from ops)
------------------------------------
- LLM 401 on custom endpoint → check CUSTOM_LLM_API_KEY in .env (restart bot).
- Mongo LLM override → LLMConfiguration collection; use upsert script or revert.
- Tool loop / recursion limit 25 → model keeps calling tools (Nemotron on Fireworks
  observed); not missing tool output — graph hits LangGraph step cap.
- contextual_query vs main_stream → different LLMPurpose; cq uses gpt-4.1-mini
  by default; main_stream can be overridden to custom/Fireworks separately.
- Check logs for: LLM_CONFIG_RESOLVED, LLM_INVOCATION_*, TOOL_CALL_RESULT,
  REQUEST_FAILED_WITH_ERROR, Recursion limit.
